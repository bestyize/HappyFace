# HappyFace 软件阶段实施计划 v0.1

日期：2026-09-23

## 1. 产品目标与边界

第一阶段先把 HappyFace 做成可使用、可分享的「有生命感的表情角色」，用软件验证用户是否愿意让它常驻桌面或闲置手机，再将同一套表情核心装入 Android 智能盒子。

- 表情占满矩形屏幕；猫耳及其他配件都属于屏幕外的可装配硬件，不进入通用表情画布。
- 表情通过参数组合生成，允许基础形态之间连续过渡。呼吸、眨眼、视线和触碰反应由本地引擎持续生成。
- 第一批交互以点击、触摸、鼠标和文字输入为主。语音识别与语音合成不是首发条件。
- 简单触碰由本地立即处理；需要理解语言时，才调用 DeepSeek 文本接口取得回复和高层表情意图。云端不负责逐帧动画。
- 同一个 Kotlin 表情核心面向网页、Windows、macOS、Android、iOS 和后续机器人；各系统的窗口、输入和系统小组件分别适配。
- 三种目标硬件屏幕从一开始进入回归矩阵：800×480（5:3）、400×320（5:4）、320×240（4:3）。手机竖屏另设布局规则，不能将盒子横屏画面直接裁切。

**实施前提：**时间按约 2 名开发者及兼职视觉设计/动效设计估算；暂无最终主板，因此性能指标先在代表性 Android 设备验证，再以量产候选硬件复测。阶段可以部分并行，总日历时间以实际人员和设备到位情况调整。

## 2. 推荐技术结构

| 模块 | 职责 | 交付形态 |
| --- | --- | --- |
| `expression-core` | 参数、角色状态、事件响应、插值、微动作、随机种子、动作优先级；不依赖窗口和云服务 | Kotlin Multiplatform 库 |
| `expression-ui` | 在统一坐标规则上绘制眼睛、嘴巴、光效和过渡；适配不同屏幕比例 | Compose Multiplatform Canvas |
| `interaction` | 将点击、拖动、悬停、文字和将来的语音识别结果映射为语义事件 | 共享协议 + 平台输入适配 |
| `cloud-gateway` | 代理 DeepSeek 请求，校验表情指令，管理额度；服务密钥保留在服务端 | 轻量服务端 |
| 平台应用 | 浏览器页面、Windows/macOS 悬浮小窗、Android/iOS 全屏应用 | 独立入口与打包 |
| 小组件适配 | 从共享角色状态生成摘要或快照，点击进入完整应用 | Android Glance/RemoteViews、Apple WidgetKit；Windows Widgets 视需求 |

**模型指令示例：**`mood=curious, intensity=0.55, gaze=left, holdMs=2200`。本地对字段进行白名单、范围和时长校验，并把它转为连续动画；模型不能任意绘制像素或改写引擎代码。微动作在没有网络时照常运行。

**技术闸门：**Compose 的 Android、iOS、桌面支持比较成熟；网页端仍需验证浏览器兼容、首屏加载和绘制表现。若网页端未达标，保留 Kotlin 共享核心，单独实现轻量网页绘制层；不要把已经做好的 Android 表情核心推倒重写。若未来某款 Android 主板上 Compose 绘制不达标，也只替换 Android 绘制层。

## 3. 阶段与交付物

| 阶段 | 参考用时 | 开发内容 | 可验收的交付物和通过条件 |
| --- | --- | --- | --- |
| P0 范围与可行性 | 第 1–2 周 | 统一视觉规则、屏幕适配方案和工程结构；分别跑通 Android 实机、桌面、手机浏览器的一个呼吸/眨眼原型 | 表情参数 v0.1、交互清单、三个硬件画布预览、最小工程；记录各端启动时间、帧率、内存及浏览器异常，决定网页是否使用共享 Compose 绘制 |
| P1 表情内核 | 第 3–5/6 周 | 8–12 个基础形态、参数组合、连续插值、眨眼/呼吸/视线、触碰事件、优先级和状态回退；做开发者参数面板 | 可复现的表情场景集、参数协议 v1、动画演示；从任意表情切换时无明显跳帧，三种分辨率没有关键部位被裁切，本地触碰能立即得到视觉反馈 |
| P2 网页公开测试版 | 第 6–8/9 周 | 即点即玩的网页/PWA；鼠标/触摸互动；文字输入经服务端调用 DeepSeek；简易分享入口、匿名使用额度与使用数据 | 可访问链接、移动/桌面浏览器兼容清单、云服务成本与故障记录；不用登录也能体验基础互动，断网后仍保留本地表情与触碰反应 |
| P3 电脑悬浮伙伴 | 第 9–11/12 周 | Windows/macOS 可移动缩放的小窗、显示层级选项、启动/退出入口、文字对话入口、暂停或降低动效机制 | 安装包和使用说明；验证多显示器、不同缩放比例、睡眠唤醒、长时间运行；小窗不会阻挡基本桌面操作，关闭后不遗留进程 |
| P4 手机全屏应用 | 第 11–14/16 周 | Android/iOS 全屏角色，手机横竖屏适配、触摸交互、文字对话、亮度/待机设置；Android 端增加盒子屏幕配置 | 两端可安装测试包；三种盒子分辨率和常见手机比例均可正常展示，前后台切换后角色状态正确恢复，连续运行无明显资源增长 |
| P5 小组件与分发优化 | P4 后 1–3 周，按反馈决定 | Android/iOS 角色状态小组件、点击进入完整应用；整理引导、分享和留存数据 | 小组件表达角色当前状态且能正确打开应用；明确它是角色摘要，持续逐帧表情仍由完整应用负责 |

**推荐发布节点：**P2 发网页公开测试版；P3 发电脑桌面伙伴测试版；P4 发手机测试版。P5 依据真实用户对小组件的需求再排期，不作为 P2–P4 的上线阻塞项。

## 4. 第一版功能清单

### 必须有

1. 满屏表情画布及三种盒子横屏比例、手机竖屏的独立布局规则。
2. 8–12 个基础表情以及连续的参数组合；从当前运动状态自然过渡。
3. 闲置时的呼吸、非固定间隔眨眼和小幅视线变化；注意降低重复感。
4. 点击/触摸/悬停/拖动中的适用动作；长按与拖动的语义不能与桌面小窗移动操作冲突。
5. 文字输入触发 DeepSeek 回复及表情意图；云端失败时回到可交互的本地状态。
6. 参数调试与事件回放工具，方便设计师微调动作而不必修改业务逻辑。
7. 服务端密钥保护、基础限额和成本统计，防止公开测试期间接口被滥用。

### 根据数据增加

- 可分享的表情片段或角色链接；分享内容默认不包含私人对话。
- 角色风格、眼睛形态和配色的有限个性化。
- Android/iOS 系统小组件；Windows Widgets Board 入口。
- Android 动态壁纸，以及 Windows/macOS 壁纸形式的独立技术验证。
- 语音、图片识别、相机、与机器人身体部件的同步动作。

## 5. 验收方法与决策点

| 时间点 | 必须回答的问题 | 具体检查 |
| --- | --- | --- |
| P0 结束 | 当前 Compose 网页实现是否适合公开传播？Android 小屏表现是否可接受？ | 在 iPhone Safari、Android 浏览器及目标级别 Android 设备检查首屏、画面、输入、帧率和内存；不合格则只换网页绘制层或优化渲染 |
| P1 结束 | 角色是否显得有生命，且持续观看不机械？ | 设计走查：至少连续观察闲置、触碰、文字回应各场景；检查眨眼节奏、视线、动作幅度、状态打断与回退；三种屏幕截图对比 |
| P2 结束 | 用户是否愿意再次打开或分享？ | 观察首次互动完成率、次日/第七日回访、每次使用的互动次数、分享及云端调用成本；用真实数据决定是否增加个性化或语音 |
| P3/P4 结束 | 常驻和全屏体验是否可靠？ | 实机长时间运行、多屏、睡眠唤醒、横竖屏、前后台恢复；记录崩溃、卡顿、内存变化和设备发热 |

此处的指标先定义**测量方法和发布闸门**，不凭空承诺量产主板的帧率或续航；在 P0 得到第一轮实测后填入具体数值目标。

## 6. 与智能盒子阶段的接口

软件阶段就约定 `InteractionEvent -> ExpressionIntent -> RenderState` 的版本化协议。盒子阶段接入麦克风、扬声器、摄像头、Wi‑Fi、蓝牙和外部耳朵/尾巴时，新增平台适配和事件来源即可。规划中的云端分工是 DeepSeek 负责文本与图片理解、腾讯云负责 STT/TTS；任何一个云端请求都不应阻塞本地眨眼、呼吸和触碰反馈。

建议在 P4 后单列「盒子预备里程碑」：开机直达表情、离线基础状态、外设事件接口、代表性主板连续运行、网络恢复，以及语音与图像服务的端到端演示。具体时间等待主板、麦克风/扬声器和摄像头方案确定后再估算。
